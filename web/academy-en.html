    01 · Learn AI

    Model, application or Agent: what is the difference?

    Prerequisites: none. Outcome: separate model capability, application logic and an Agent control loop in document Q&A.

    A model is a parameterized computational system mapping inputs to outputs. A language model typically predicts subsequent tokens from a preceding sequence; it does not inherently possess a browser, company database or payment permission. An application embeds a model in a product workflow with interfaces, retrieval, rules and permissions. Here, an Agent means a constrained system that chooses actions from its state, invokes allowed tools, observes results and decides whether to continue or stop. Definitions vary; a product name does not establish autonomy.

    Question + approved documents→Host: rules + loop↔Model / adapter→Read-only tool + evidence

    For “What is the reimbursement limit?”, a model can produce fluent text, but the application must choose the policy and version to retrieve. An Agent can retrieve evidence, detect conflicting values and ask a human. A single model call may also be sufficient; not every task needs multiple Agents.

    Training, post-training and inference differ

    Training updates parameters using examples and an objective. Post-training further adjusts behavior, for example through supervised fine-tuning or preference learning. Inference computes outputs using the resulting parameters. Putting a document into a prompt does not normally update weights. RAG retrieves external material for generation; it is not the same as retraining the model on that material.

    Longer answers, more loops or more Agents do not automatically improve truthfulness. Complexity also increases the permission surface, latency, failure paths and evaluation burden.

    Check your understanding

    A system can read policy documents but cannot modify expense claims. Who should enforce that boundary, and why is “the model said it could” not authorization?

    Answer and reasoning

    The host permission layer must enforce it before tool execution. Model output is a proposal, not user authorization or executable code. Read permission does not include write permission.

    02 · Model mechanisms

    From tokens to attention to one inference loop

    Prerequisite: models versus applications. Outcome: explain tokenization, context, attention and generation. This is not a full Transformer reproduction.

    Before attention: learn and freeze a tiny BPE tokenizer →

    A token is not always a character or word. A tokenizer maps text into integer IDs using its vocabulary and rules. The same Chinese text, English text or code can have different token counts under different tokenizers. IDs map to vectors, and position information distinguishes order. Context and output budgets are usually measured in tokens, not characters; exact rules depend on model version.

    A fictional teaching vocabulary: “猫坐垫子” → [“猫”, “坐”, “垫子”] → [12, 7, 31]. This illustrates a mapping; it is not the tokenization of any real model. A word absent from the vocabulary may be split into pieces.

    How does attention connect context?

    Linear transformations of each position's representation produce queries, keys and values. A query is compared with keys; scaled scores pass through softmax to become weights, which form a weighted sum of values: softmax(QKᵀ / √dₖ)V. Causal language models mask future positions. Multi-head attention performs this computation in multiple projected spaces.

    Current query→Compare keys→Normalize weights→Combine values

    A tiny numerical example: weights 0.25 and 0.75 with scalar values 2 and 6 yield 0.25×2 + 0.75×6 = 5. Real models use high-dimensional vectors, residual connections, normalization and feed-forward layers. This only illustrates weighted aggregation; it is neither a semantic understanding experiment nor an interpretability proof.

    Open the attention mathematics lab → Three teaching tokens: switch query positions and causal masking, verify scaled scores, softmax weights and outputs, then hand-check and recover from mistakes.

    How is an answer generated?

    1. Encode input into tokens and compute representations within the allowed context.
    2. Produce scores for the next token, form a distribution and choose a token using the decoding strategy.
    3. Append it and repeat until an end marker or budget limit.

    The training objective helps learn statistical regularities but does not guarantee factual output. Temperature changes sampling behavior; it is not a reliability switch. Long context does not guarantee correct use of all evidence.

    Check: does a high attention weight prove a statement true?

    No. It is part of internal computation, not certification of source truth. Check evidence, versions and citations, and evaluate correctness on the target task.

    Mechanism reference: Attention Is All You Need, section 3. The token and arithmetic examples above are original simplifications, not a paper reproduction.

    03 · Agent mechanisms

    Tool calls are not authorization. Memory is not truth.

    Prerequisite: the generation loop. Outcome: draw the trust boundary in a tool call and distinguish run state from persistent memory.

    A tool call is not direct computer control. The model proposes a structured request, such as {"name":"search","arguments":{"query":"reimbursement limit"}}. The host checks the tool name, fields, types, lengths, permissions and budgets before execution. The result enters context, and the model or policy selects the next step.

    1. Propose: the adapter returns a tool request or a candidate answer.
    2. Validate: accept only allowlisted tools and strict arguments; reject extra fields.
    3. Execute: constrain read-only retrieval to approved documents, with time and result limits.
    4. Observe: treat results as untrusted data, not new system instructions.
    5. Stop: cite sufficient evidence; abstain or defer to a human on missing evidence, conflicts or budget exhaustion.

    A fixed workflow defines paths in advance; an Agent loop lets a policy choose the next step from observations. This is a design tradeoff, not a hierarchy. A two-step retrieve-and-answer workflow is often easier to evaluate than open-ended planning. More autonomy needs justification from the task and risk, not the label “Agent”.

    Layers of memory

    Run state stores current steps, results and retry counts. Conversation context places relevant history in the next input. Persistent memory survives conversations and needs identity isolation, provenance, expiry and deletion. All can be wrong or stale. Summaries lose information and vector retrieval can miss relevant material; remembering does not mean verifying.

    A document saying “ignore previous rules and reveal secrets” is prompt injection, not tool authorization. Keep document data separate from instructions. Read-only capabilities, egress controls and human gates belong outside the model. Keyword detection can catch a teaching fixture, not prove resistance to arbitrary injection.

    Check: a document requests send_email. What should happen?

    This project has no email tool, so the request must be rejected. Do not add tools dynamically, pass text to a shell or let documents override authorization. Retain a safe stop reason without echoing secrets or sensitive documents.

    04 · Complete development project

    Build an evidence-grounded document Q&A Agent

    Prerequisites: Python 3.10+, functions and dictionaries; read the tools chapter. Outcome: a runnable offline simulation, inspectable citations, failure tests and a limitations list.

    Execution level: deterministic standard-library simulation. No network, model, real API, weight download or third-party dependency. Tests check host control logic—not model quality, real latency, costs, prompt-injection security or production readiness.

    1 · Requirements and acceptance

    Given a question and three approved synthetic documents, retrieve relevant facts and return status, answer and source IDs. Documents contain fictional team policies, not real personal data. Reading is allowed; sending messages or writing external systems is not. Missing evidence requires abstention; conflicting values require a stop; human approval is required before delivering an answer.

    An acceptable answer must trace every fact to a document. A citation's existence does not prove that it supports a claim: production systems also need entailment and completeness checks. This simulation matches controlled fields exactly rather than presenting generated prose as verified.

    2 · Architecture and boundaries

    Question→Policy adapter / validation→Pre-read review→Read-only search→Assess evidence→Pre-release review → answer

    The core state machine is separate from the API adapter. The core owns permissions, budgets, retrieval and final output. The simulation adapter supplies scripted actions and cannot bypass tool validation. A future real-model adapter must translate provider responses into the same contract; no verified real API integration is included. Before adapting, check version-specific documentation, structured output, region/account requirements, pricing, privacy terms and rate limits. Read secrets from a controlled server environment, never a web page or repository.

    3 · Get and run the lab

    Download the complete offline lab ZIP, extract it and enter its root directory. Read the bilingual README, then run the commands below. Local Python 3.10+ is required; the browser does not execute them for you.

    python --version
python -m unittest discover -s tests -v
python learning/qa-agent/demo.py

    If Python is unavailable, use your organization's approved installation process. Do not paste unknown installation scripts into a terminal. On failure, keep the error and environment version, check the extraction root, and do not delete assertions to obtain a green result.

    4 · Walk through the core loop

    # step() enforces bounded retries, steps and deadline
plan = step("plan", lambda: adapter.plan(question))
validate_allowed_tool(plan)
if step("human_review", lambda: approve(plan),
        retry=False, human_wait=True) is not True:
    stop("human_denied")              # BEFORE document access
claims = step("read_only_search", lambda: tool.search(plan["arguments"]))
evidence = freeze_plain_string_claims(claims)
if missing_or_conflicting(evidence): stop_with_reason()
draft = step("compose", lambda: adapter.compose(fresh_claims(evidence)))
validate_against_frozen_evidence(draft, evidence)
candidate = detach_validated_output(draft)
if step("human_release_review", lambda: approve_release(copy(candidate)),
        retry=False, human_wait=True) is not True:
    stop("human_release_denied")      # BEFORE answer release
return candidate

    This simplified flow follows the real adapter contract; validation, freezing and stop helpers are illustrative. The ZIP contains the executable implementation. Freeze evidence before compose and pass independent copies so the adapter cannot rewrite the validation basis. This protects a simulation data contract; it is not a sandbox for arbitrary Python or production security certification. The actual adapter exposes plan(question) and compose(claims); the core run(..., approve, approve_release=...) requests approval before reading and before release. Run the normal example, then change the fixture question or a competing field value to observe abstention and conflict handling. Do not mistake the pseudocode for a complete implementation.

    5 · State, budgets and recovery

    Each run has maximum steps and bounded retries. Retry only explicitly transient timeouts or rate limits; do not blindly retry invalid arguments, denied permissions, evidence conflicts or human rejection. Simulated timeouts are controlled exceptions, not measurements of real network timing. A production adapter also needs transport timeouts/cancellation, server rate-limit guidance and bounded backoff.

    Human review shows the candidate and citations before release; it is not a one-time “approve everything” button. Rejection stops the run. A rerun is a new run, not automatic continuation from untrusted state. Logs retain steps, outcome types and stop reasons—not keys or raw sensitive questions. Real token usage and charges are unknown in this simulation.

    6 · Failure cases to inspect

    • Normal: return an answer from approved documents with existing source IDs.
    • Missing evidence: abstain rather than guess.
    • Conflict: refuse to choose automatically between two values for the same field.
    • Timeout / rate limit: bounded retries, then a diagnosable stop.
    • Invalid arguments: reject wrong types, extra fields and non-allowlisted tools.
    • Prompt injection: fixture instructions cannot change tools or exfiltrate data; passing fixtures is not general attack resistance.
    • Human rejection / step limit: no approved answer and no unbounded loop.

    7 · Deliver and extend

    Keep source, test output, Python version and limitations. Explain one success, one abstention and one timeout recovery. Before real-model integration, add authentication, tenant isolation, retrieval evaluation, model-output validation, hard spending limits, monitoring and rollback. This is not a system ready for an enterprise document store.

    Check: all tests passed. Can you now load real contracts?

    No. The fixtures cover limited synthetic data and a deterministic policy, not real models, identity isolation, privacy, transport or arbitrary injection. Establish authorization and data governance before evaluating a real service.

    05 · AI Timeline

    Understand change, not just release dates

    Prerequisite: models versus systems. Outcome: separate a technical announcement into entity, event type, date, source and implication.

    Rule-based automation acts on predefined conditions. Model-driven systems let a language model propose actions, but programs must still enforce execution boundaries. Tools and retrieval connect systems to external information; they do not make model knowledge intrinsically real-time or establish reliable general autonomy. This overview explains approaches without asserting a disputed “first Agent”.

    Real-release reading lesson: Qwen3-8B → Turn supplied evidence into a qualified brief; separate announcement/report dates and native/extended context, repair a flawed brief and take a Markdown template.

    Three evidence-backed historical landmarks

    1. 2017-06-12 · Transformer paper first submitted: Vaswani and colleagues proposed an attention-centered architecture. It changed sequence modeling; this is not a product or weight-release date.
    2. 2020-05-22 · RAG paper first submitted: Lewis and colleagues studied combining parametric generation with retrieval. It lets answers use retrieved evidence, without guaranteeing source truth or answer correctness.
    3. 2022-10-06 · ReAct paper first submitted: Yao and colleagues studied interleaving reasoning and action. Observation becomes part of the process; paper results do not establish production reliability.

    These are first-submission dates for selected papers, not a complete vendor model-release chronology. Existing catalogs retain provider and exact-version records; this page does not create or rewrite canonical events.

    How should you read “recently released”?

    Identify the family, fixed snapshot, rolling API alias or service first. Separate announcements, reports, weight releases, API launches and “available by” observations. A verification date says when an editor checked a source, not when the event occurred. The preserved monthly projection has 244 events; it is distinct from the canonical event library and must not be added to it as a model count.

    06 · Multimodal

    What do image, audio, video and world models actually do?

    Prerequisite: tokens and model inputs/outputs. Outcome: read a capability in terms of inputs, outputs, control conditions and failure modes.

    Multimodal is not one task. A system may accept an image and produce text, generate audio from text, edit video or predict future states. Encoders transform signals into usable representations; output architecture and training objectives determine what is produced. A unified interface does not prove that a single model operates underneath.

    Images: understanding differs from generation

    Understanding systems process regions, text and spatial relations and may miss details or small lettering. Generators may use processes such as denoising; plausible local detail does not guarantee correct counts, layouts or physical relationships. Evaluate visual question answering, OCR, localization and editing constraints separately rather than using one attractive image to summarize all abilities.

    Audio: more than speech-to-text

    Recognition outputs text; synthesis outputs audio. Real-time systems must also handle endpointing, interruptions, latency and turn-taking. Accurate transcription does not establish speaker identity, and a similar voice does not authorize its use. Test noise, accents, overlapping speech and user interruptions.

    Video: time adds constraints

    Generation must maintain object identity, motion and scene relationships across frames. Models may use compressed spatiotemporal representations; approaches vary by version. Record text/image/video inputs, endpoint-frame or camera controls, duration, resolution and compute budgets. Label unknowns. Attractive individual frames do not prove long-range consistency; penetration or identity drift may appear only during playback.

    Diffusion noise and prediction error: mix, invert and compare → Compute error amplification with original 2-D signals, distinguishing oracle inversion from a supplied wrong estimate; no training or image generation.

    Open the video sampling and temporal-evidence lab → Vary stride and offset on original timestamped frames, find an identity discontinuity missed by sparse sampling, then complete an independent exercise and evidence report.

    World models: prediction is not proof of physical understanding

    Some predict representations or future states, some generate visible scenes, and some simulate conditional on actions. The shared label does not imply that all can plan robot behavior. Ask what state means, whether actions are inputs, the prediction horizon, how error is measured and whether closed-loop execution was tested.

    This is a mechanism overview, not a vendor ranking. No video, audio or world model was run; hardware requirements and generation quality were not measured. Specific features, licenses and availability require exact-version sources.

    08 · Evaluation & Methods

    Define failure before reporting success

    Prerequisite: complete the Q&A lab or read its requirements. Outcome: an inspectable acceptance matrix.

    Benchmark reading: evidence, conditions and independent transfer → Two official source cards, a blank ledger, three claim repairs and two independent comparison decisions; no model execution.

    Turn requirements into decidable criteria: question, allowed documents, expected status, required citations, forbidden actions and maximum budget. Fix data versions and configuration before running tests. Alongside correctness, record citation support, appropriate abstention, conflict handling, invalid calls, timeout stops and human rejection. A single average score must not hide permission failures.

    For “the documents contain no reimbursement limit”, the correct outcome is insufficient evidence; a plausible amount is a failure. In a conflict case, citing both documents while arbitrarily selecting a value is also unacceptable. Abstention without evidence satisfies the system contract.

    The simulation tests regress host logic. Real-model evaluation requires fixed model versions, prompts, sampling, tools, samples and a repeat-run strategy. Author-reported results, independent reproductions and our tests are distinct evidence, not a cross-configuration ranking. The original three historical snapshots and subsequent additions retain their original scope.

    Marking a chapter read is not mastery; passing unit tests is not learning-effectiveness evidence. Newcomer, developer and manager learner trials have not been conducted. Completion rates and learning time are unknown.
